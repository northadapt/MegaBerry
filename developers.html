Getting started

Get an API keyCreate a key in Settings and choose the scopes it needs. List your modelsRead each model's input contract at startup. Submit a generationSend a prompt with an idempotency key, then poll it. Get the resultDownload the outputs, or receive a signed webhook when it finishes.

What you can do

GenerateImages and videos with any model your plan includes, one at a time or in bulk.
UploadSend source images, videos and audio once and reuse them across generations.
Analyze and editDescribe images, analyze videos, caption, remove objects and extract frames.
Get notifiedSigned webhooks tell your server the moment a generation completes.

Get an API key

  1. Sign in and open Settings → Developer API.
  2. Create a key: give it a name, choose its permissions, choose when it expires (or no expiry), and accept the Developer API Terms. Permissions come in plain-word groups that map to the scopes below. Only read access is selected at first: add only what your integration needs.
  3. Copy the key. It starts with tjp_sk_live_ and is shown only once: store it in a secret manager or an environment variable, never in source control.
The key is shown onceCopy it when you create it. If you lose it, rotate the key in Settings to get a new secret.

Who can create keys

  • Accounts on the Pro or Max plan with an active subscription.
  • With a verified email address.
  • In good standing: the account is active, its Developer API access is not suspended, and it has broken no content rule in the last 30 days.

Creating keys yourself is rolling out in phases. Settings → Developer API lists any requirement your account does not meet yet. Until self-serve keys reach your account, the page offers Request API access instead: tell us which scopes you need and our team issues the key. Training permissions are issued by our team only.

Using the API at all needs a plan that includes it: requests from an account whose plan does not include Developer API access answer 403 forbidden.

Managing keys

  • Use separate keys for separate integrations so you can revoke one without touching the others. An account can hold a limited number of working keys; revoke one to create another.
  • Rotate a key in Settings to get a new secret with the same name and permissions, then deploy the new one. The old key keeps working for up to 24 hours (never past its own expiry) unless you cut it off now: do that when a key has leaked.
  • You accept the current Developer API Terms when you create or rotate a key. After the terms change, you accept the new version the next time you do either; your existing keys keep working meanwhile.
  • Revoking takes effect on the key's next request. A revoked or expired key answers 401 unauthorized.
  • Keys issued before this format start with sk_. They keep working, and everything on this page applies to them too.

Quickstart

List the models your key can use, pick one that runs on a prompt alone, submit a generation with an idempotency key, poll it until it finishes, then download the outputs. A model runs on a prompt alone when its supports_avatar is false, its input_schema has a prompt property and lists no other required field, and its batch_size_min is null or 1.

supports_avatar: true means a model accepts an avatar, not that it runs without one, so the samples never pick such a model; when no model qualifies they stop with a message instead of submitting. Other models may need more: an avatar, upload ids for their media fields (see Files and uploads), the options their schema requires, or a larger batch_size.

#!/usr/bin/env bash
# Save as quickstart.sh and run: API_KEY="tjp_sk_live_..." bash quickstart.sh
# Your key is in Settings » Developer API. Needs curl 7.76 or later, and jq.
set -euo pipefail
: "${API_KEY:?Set API_KEY to your Developer API key}"

# 1. List the models your key can use and pick one that runs on a prompt alone:
#    supports_avatar is false (it takes no avatar, so it cannot need one), its
#    input_schema has a "prompt" property and requires no other field, and its
#    batch_size_min is null or 1.
MODELS=$(curl -sS --fail-with-body "https://api.megaberry.com/v1/models" \
  -H "Authorization: Bearer $API_KEY") \
  || { echo "Listing models failed: $MODELS" >&2; exit 1; }
MODEL_ID=$(jq -r '[.data[]
  | select(.supports_avatar == false)
  | select(.input_schema.properties.prompt != null)
  | select(((.input_schema.required // []) - ["prompt"]) == [])
  | select((.batch_size_min // 1) <= 1)]
  | .[0].id // empty' <<< "$MODELS")
if [ -z "$MODEL_ID" ]; then
  echo "No model your key can use runs on a prompt alone: read each model's input_schema and supports_avatar" >&2
  exit 1
fi
echo "model: $MODEL_ID"

# 2. Submit a generation. Reuse the same Idempotency-Key if you retry this request.
GENERATION=$(curl -sS --fail-with-body "https://api.megaberry.com/v1/generations" \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1042-render-1" \
  -d "{\"model\": \"$MODEL_ID\", \"prompt\": \"A ceramic mug on a wooden table, soft morning light\"}") \
  || { echo "Submit failed: $GENERATION" >&2; exit 1; }
GENERATION_ID=$(jq -r '.id' <<< "$GENERATION")
echo "generation: $GENERATION_ID"

# 3. Poll, with a pause between requests, until the generation finishes
while :; do
  RESULT=$(curl -sS --fail-with-body "https://api.megaberry.com/v1/generations/$GENERATION_ID" \
    -H "Authorization: Bearer $API_KEY") \
    || { echo "Polling failed: $RESULT" >&2; exit 1; }
  STATUS=$(jq -r '.status' <<< "$RESULT")
  case "$STATUS" in
    succeeded | partially_succeeded | failed | rejected | canceled) break ;;
  esac
  sleep 5
done
echo "status: $STATUS"

# 4. Download each output (items[].outputs[].url is a signed link, valid for 7 days)
jq -r '.items[].outputs[] | select(.url != null)
  | "\(.id).\(.mime_type | split("/")[1]) \(.url)"' <<< "$RESULT" \
  | while read -r FILE URL; do
      curl -sS --fail-with-body -o "$FILE" "$URL"
    done
// Save as quickstart.mjs and run: API_KEY="tjp_sk_live_..." node quickstart.mjs
// Needs Node 18 or later.
import { writeFile } from "node:fs/promises";

const API = "https://api.megaberry.com/v1";
const auth = { Authorization: `Bearer ${process.env.API_KEY}` };

async function call(path, init = {}) {
  const res = await fetch(API + path, { ...init, headers: { ...auth, ...init.headers } });
  const body = await res.json();
  if (!res.ok) {
    const e = body.error ?? {};
    throw new Error(`${res.status} ${e.code}: ${e.message} (request_id ${e.request_id})`);
  }
  return body;
}

// 1. List the models your key can use and pick one that runs on a prompt alone
const { data: models } = await call("/models");
const model = models.find((m) =>
  m.supports_avatar === false &&
  m.input_schema.properties?.prompt &&
  (m.input_schema.required ?? []).every((f) => f === "prompt") &&
  (m.batch_size_min ?? 1) <= 1);
if (!model) throw new Error("No model your key can use runs on a prompt alone");
console.log("model:", model.id);

// 2. Submit a generation. Reuse the same Idempotency-Key if you retry this request.
let gen = await call("/generations", {
  method: "POST",
  headers: { "Content-Type": "application/json", "Idempotency-Key": "order-1042-render-1" },
  body: JSON.stringify({ model: model.id, prompt: "A ceramic mug on a wooden table, soft morning light" }),
});
console.log("generation:", gen.id);

// 3. Poll, with a pause between requests, until the generation finishes
const finished = ["succeeded", "partially_succeeded", "failed", "rejected", "canceled"];
while (!finished.includes(gen.status)) {
  await new Promise((r) => setTimeout(r, 5000));
  gen = await call(`/generations/${gen.id}`);
}
console.log("status:", gen.status);

// 4. Download each output (url is a signed link, valid for 7 days)
for (const item of gen.items) {
  for (const out of item.outputs) {
    if (!out.url) continue;
    const bytes = Buffer.from(await (await fetch(out.url)).arrayBuffer());
    await writeFile(`${out.id}.${out.mime_type.split("/")[1]}`, bytes);
  }
}

Authentication

Send your key in the Authorization header as a bearer token. X-API-Key is accepted as an alternative. Keys are never accepted in a query string. A missing, revoked or expired key answers 401 unauthorized.

curl https://api.megaberry.com/v1/credits \
  -H "Authorization: Bearer $API_KEY"
curl https://api.megaberry.com/v1/credits \
  -H "X-API-Key: $API_KEY"

Every response carries our id for the request in the X-Request-ID header, and errors repeat it as request_id: log it and include it when you contact support. You may send your own X-Request-ID to correlate with your logs. It is never used as the request id, but a plain value (8 to 64 letters, digits or hyphens, such as a UUID, that does not look like a key) is echoed back in X-Client-Request-ID.

Rate limits and plan limits

The API follows your plan's limits and adds rate limits of its own. Generations you start through the API count against the same plan limits as generations you start on the site: daily generations, generations running at once, batch size, storage and your credit balance. What your plan cannot do on the site, it cannot do through the API. Your plan is on the plans page.

On top of that, the API limits request rates (per account, per key and per client address), generation throughput, and daily and monthly credit spend. These limits can only make your plan's limits tighter, never looser, and they can differ between accounts. A request refused by the per-key limit does not count against your account's request limit.

  • 429 rate_limited: too many requests, too many generations running or starting at once, or too many failed authentication attempts from one address. Slow down and retry.
  • 429 quota_exceeded: a daily or monthly limit is reached (generations or credit spend), or too many uploads are waiting to be used. Retrying soon fails the same way: wait for the limit to reset, or use the uploads you already created.
  • 402 insufficient_credits: your balance cannot cover the request.

A rate-limited response carries Retry-After (in seconds) whenever the wait is known: never retry sooner. Responses may also carry RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset (and the same values as X-RateLimit-*), describing the request-rate limit closest to running out; not every 429 has them. Back off exponentially on 429 and 5xx, with jitter, especially when there is no Retry-After. Upload creation and frame extraction have their own short-term limits so one integration cannot crowd out others.

Idempotency

Send an Idempotency-Key header on requests that create billable work, and reuse the same key when you retry after a timeout or a network error. Keys are 1 to 256 letters, digits, dashes or underscores. Tie the key to your own job (for example order-1042-render-1) rather than generating a new one per attempt.

  • The same key with the same body within 24 hours replays the original response instead of creating a second generation.
  • The same key with a different body, or while the first request is still running, answers 409 idempotency_conflict.
  • One exception, for POST /v1/generations and POST /v1/generations/bulk only: if every earlier attempt with the key was refused before anything was submitted (for example an unknown model, invalid input or a rate limit), you may send a corrected body with the same key, and the key then belongs to the corrected body. Once an attempt may have been submitted, only the original body can use the key. Analysis and tool requests always keep their original body.
  • Keys are scoped to your account, the API key that sent them and the endpoint. Finish retries before rotating an API key.

These operations honour the header; others ignore it:

  • POST /v1/generations
  • POST /v1/generations/bulk

A submitted generation can still fail later. Each failed, rejected or canceled item has a human-readable error (show it, do not parse it) and a stable error_code (branch on it). So does a succeeded item whose output is withheld (access_denied, see Content rules). The generation itself carries the most common item code when the whole generation failed, was rejected or was canceled. Webhooks

Instead of polling, register an HTTPS endpoint and receive a signed POST when a generation finishes. Creating an endpoint returns its signing secret (whsec_...) once; store it with your other secrets.

Create an endpoint
curl https://api.megaberry.com/v1/webhooks \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://your-app.example/webhooks/generations", "events": ["generation.completed"]}'

Events

  • generation.completed: a generation reached a final status. The body has the generation id, status, generation-level error_code, credits and your metadata, but no output links: fetch the generation for fresh links.
  • webhook.test: sent by the test operation to check your endpoint. You cannot subscribe to it.

Omit events (or send an empty list) to receive every event type. An account can register up to 16 endpoints.

Verify the signature

Every delivery carries a Studio-Signature header: t=<unix seconds>,v1=<hex HMAC-SHA256>, computed over {t}.{raw request body} with your endpoint secret. Recompute it over the exact bytes you received, compare in constant time, and reject timestamps more than five minutes old.

Delivery headers
Content-Type: application/json
Studio-Signature: t=1760788808,v1=5f2b...e9   # HMAC-SHA256 of "{t}.{raw body}", hex
Studio-Event-Id: evt_...                     # same on every retry of one event
Studio-Delivery-Id: ...                      # one per delivery
User-Agent: Studio-Webhooks/1.0
import crypto from 'node:crypto'
import express from 'express'

const SECRET = process.env.WEBHOOK_SECRET // the whsec_... value shown once at creation
const TOLERANCE_SECONDS = 300

function verify(header, rawBody) {
  const parts = Object.fromEntries(
    header.split(',').map((part) => {
      const i = part.indexOf('=')
      return [part.slice(0, i), part.slice(i + 1)]
    })
  )
  const timestamp = Number(parts.t)
  if (!Number.isFinite(timestamp)) return false
  if (Math.abs(Date.now() / 1000 - timestamp) > TOLERANCE_SECONDS) return false
  const expected = crypto
    .createHmac('sha256', SECRET)
    .update(`${timestamp}.${rawBody}`)
    .digest('hex')
  const given = Buffer.from(parts.v1 ?? '')
  return given.length === expected.length && crypto.timingSafeEqual(Buffer.from(expected), given)
}

const app = express()

// Use the RAW body: re-serialized JSON will not match the signature.
app.post('/webhooks/generations', express.raw({ type: 'application/json' }), (req, res) => {
  const rawBody = req.body.toString('utf8')
  if (!verify(req.get('Studio-Signature') ?? '', rawBody)) return res.sendStatus(400)
  const event = JSON.parse(rawBody)
  // Deliveries are at-least-once: skip an event id you have already handled.
  const eventId = req.get('Studio-Event-Id')
  res.sendStatus(200) // answer quickly, then do the work
  handleEvent(eventId, event)
})
import hashlib
import hmac
import os
import time

from flask import Flask, abort, request

SECRET = os.environ["WEBHOOK_SECRET"]  # the whsec_... value shown once at creation
TOLERANCE_SECONDS = 300
app = Flask(__name__)


def verify(header, raw_body):
    parts = dict(p.split("=", 1) for p in header.split(",") if "=" in p)
    try:
        timestamp = int(parts["t"])
    except (KeyError, ValueError):
        return False
    if abs(time.time() - timestamp) > TOLERANCE_SECONDS:
        return False
    expected = hmac.new(SECRET.encode(), f"{timestamp}.".encode() + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(parts.get("v1", ""), expected)

    raw_body = request.get_data()  # the RAW body: re-serialized JSON will not match the signature

        abort(400)

    event_id = request.headers.get("Studio-Event-Id")
    handle_event(event_id, request.get_json())  # queue the work and answer quickly
    return "", 200

Retries and delivery

  • Answer with any 2xx within 10 seconds. Redirects are not followed.
  • Anything else is retried with exponential backoff (about 12 attempts over roughly half a day). Deliveries are at-least-once: deduplicate on Studio-Event-Id.
  • After 20 consecutive failed deliveries the endpoint is paused automatically. You can also pause an endpoint yourself.
  • A paused endpoint receives no events. Events that occur while it is paused are not delivered to it, not even after you resume it: fetch or list your generations to catch up. Deliveries that were already pending when it paused are held, and resuming sends them; held deliveries older than 7 days are marked failed instead.
  • You can pause and resume an endpoint, list its recent deliveries, replay a failed delivery and send a test event at any time.
  • Endpoint URLs must use HTTPS and resolve to public internet addresses.

Files and uploads

Media goes in as uploads, never as URLs or inline data: create an upload, send the bytes with a PUT to the returned upload_url, then pass the upl_ id in the model's media field (for example options.source_image). The Content-Type and size of the PUT must match what you declared.

Upload and use a file
# 1. Ask for an upload URL. size is the exact number of bytes.
curl https://api.megaberry.com/v1/uploads \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d "{\"filename\": \"photo.png\", \"content_type\": \"image/png\", \"size\": $(wc -c < photo.png)}"

# 2. PUT the bytes to upload_url with the same Content-Type
curl -X PUT "UPLOAD_URL" -H "Content-Type: image/png" --data-binary @photo.png

# 3. Pass the upl_ id in the model's media field (see its input_schema)
curl https://api.megaberry.com/v1/generations \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "MODEL_ID", "prompt": "Clean white background", "options": {"source_image": "upl_..."}}'

  • The upload URL is valid for about 15 minutes. An upload that is never used in a request expires after 24 hours; once used, you can reuse its id.
  • An account can hold only a limited number of unused uploads at once. Past that, creating an upload answers 429 quota_exceeded: use the uploads you have, or wait for unused ones to expire.
  • A model may accept less than the limits above (format, dimensions, duration). Its input_schema says what it takes.
  • Uploads count toward your account's storage, the same as uploads on the site.

Outputs

Each finished item lists its outputs with a signed download url valid for 7 days and an expires_at. Every poll of a generation returns fresh links, so store the generation id, not the link, and download what you want to keep. Treat links like passwords: anyone who has one can download the file. A url can be null briefly; poll again to get one.

Models

GET /v1/models lists the models published on the API that your account can use right now. Some models are available only to particular accounts, or to accounts that hold particular avatars; partner models are listed only when the site offers them on your plan; and adult models only to accounts eligible for adult content under the site's rules. The list changes, so read it at startup instead of hard-coding model ids. A listed model is not a reservation: plan limits, credits and content rules are checked again when you submit. Each model publishes:

  • id: what you send as model.
  • input_schema: a closed JSON Schema for the prompt and options. Unknown fields are rejected with 400 invalid_input.
  • contract_version and contract_hash: cache forms and validators by them; the version increases on breaking input changes.
  • batch_size_min, batch_size_max and supports_avatar.

          "prompt": { "type": "string", "maxLength": 2000 },

Models that take an avatar list the avatars your account can use at GET /v1/avatars, and GET /v1/models/{model}/authoring returns a model's prompt-builder options.

Partner models run one generation per request, as on the site: submit them with POST /v1/generations. POST /v1/generations/bulk refuses them with 400 invalid_input on /model. A model that runs on a partner model is listed and accepted only when that partner model is available to your account through the API; otherwise it is not listed, and requests for it answer 404 not_found or 403 forbidden.

Content rules

The same content rules as the site apply to every request, and adult content follows the site's eligibility rules.

  • Partner models do not accept adult content for any account: an adult prompt or image input answers 403 content_rejected.
  • For an account that is not eligible for adult content, every prompt and source image is screened, including caption, image and video analysis, object removal and frame extraction inputs. Adult content answers 403 content_rejected; change the content, since sending it again unchanged is refused again.
  • If screening is briefly unavailable, the request is refused with 400 invalid_request and can be retried. Video analysis can answer 429 rate_limited with Retry-After while screening is busy.
  • Eligibility is checked again later, not only when you submit. If an account stops being eligible, its adult outputs are withheld: a generation item stays succeeded with no outputs and error_code access_denied, adult work that had not started ends failed with access_denied and is not charged, and an object-removal or video-analysis result comes back without its output, also with access_denied.

Frequently asked questions

Can I call the API from a browser?

No. API keys are secrets and must never ship in a web page or a mobile app. The API sends no CORS headers, so browsers cannot read its responses anyway. Call it from your server.

Which plans include the Developer API?

Accounts on the Pro or Max plan with an active subscription, a verified email address and good standing can create keys. Using the API at all needs a plan that includes it: requests from an account whose plan does not include Developer API access answer 403 forbidden.

Do API generations use the same limits and credits as the site?

Yes. Generations you start through the API count against the same plan limits as generations you start on the site: daily generations, generations running at once, batch size, storage and your credit balance. The API adds rate limits of its own, which can only make your plan's limits tighter.

How do I retry safely without creating duplicates?

Send an Idempotency-Key header on requests that create billable work and reuse the same key when you retry after a timeout or a network error. The same key with the same body within 24 hours replays the original response.

Should I poll or use webhooks?

Either works. Polling is the simplest: check the generation every few seconds at most. Webhooks tell your server the moment a generation completes, with a signed POST; deliveries are at-least-once, so deduplicate on Studio-Event-Id.

How long do output links last?

Each finished item lists its outputs with a signed download url valid for 7 days and an expires_at. Every poll returns fresh links, so store the generation id, not the link, and download what you want to keep.

Can I send media by URL?

No. Media goes in as uploads: create an upload, send the bytes with a PUT to the returned upload_url, then pass the upl_ id in the model's media field. See Files and uploads for types and size limits.

What should I include when I contact support?

The request_id of the failing request. Every response carries it in the X-Request-ID header, and errors repeat it in the body.

Questions or a problem with the API? Contact us and include the request_id of the failing request.
